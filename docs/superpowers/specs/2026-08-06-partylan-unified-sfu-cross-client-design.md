# PartyLAN 网页端与客户端统一 SFU 兼容设计

**状态：** 已确认
**日期：** 2026-08-06
**目标节点：** 广州节点 `partylanapp.com`

## 1. 背景

当前 PartyLAN 已具备统一房间控制面、Presence、共享租约和屏幕 SFU，但媒体与界面仍是部分兼容：

- 原生客户端共享和观看使用 `/sfu-ws`。
- 网页端保留 Screego 浏览器点对点媒体，并在特定条件下切换到 `/sfu-ws`。
- 客户端加入 `origin=web` 的房间时会打开系统浏览器，而不是进入客户端原生房间。
- 网页端通过克隆 Screego MUI 成员节点补充客户端成员。该逻辑会跳过对话框中的成员列表，也可能被 React 重绘删除。
- Screego 自身成员、统一 Presence 和 SFU 连接状态仍可能产生不同视图。

这使跨端兼容依赖房间来源和网页 DOM，而不是稳定的控制面与媒体协议。广州节点当前出现的“网页可以进入客户端房间，但网页成员列表不显示客户端成员”属于这一边界内的问题。

## 2. 目标

实现以下统一行为：

1. 所有网页端和客户端房间的屏幕媒体均使用 `/sfu-ws`。
2. 客户端加入任何来源的房间都进入原生界面，不再为兼容而打开网页。
3. 网页端继续保留登录、房间页面和浏览器采集能力，不破坏既有网页访问。
4. `/api/presence` 成为网页端和客户端成员列表的唯一事实来源。
5. `/api/room-state` 与共享租约成为共享者、媒体阶段和房间媒体模式的唯一事实来源。
6. 网页端和客户端均可成为共享者，所有网页端和客户端均可观看。
7. 同一房间同一时间只允许一个共享者。
8. 共享视频统一为 H.264，共享音频统一为 Opus 48 kHz 双声道。
9. 房间语音继续使用独立 `/voice-ws`，不得进入屏幕共享音轨。
10. 迁移、部署和回滚不得影响广州节点网页首页、登录、建房、加入及历史房间访问。

## 3. 已确认的方案

采用“保留现有控制面，屏幕媒体渐进式全面收敛到 SFU”的方案。

不采用以下方案：

- 不重建完整的 PartyLAN 专用网页房间应用。
- 不让客户端同时维护 Screego P2P 和 GameCast SFU 两套原生媒体协议。
- 不使用按观看端静默回退 P2P 的混合模式。

Screego P2P 仅在迁移期间保留为房间级回滚能力，不再作为最终正常流程的一部分。

## 4. 总体架构

```text
网页端 ───────┐
              ├─ /api/presence ─ 统一成员列表
原生客户端 ──┘

网页端 ───────┐
              ├─ /api/room-state + /api/share/* ─ 房间与唯一共享租约
原生客户端 ──┘

浏览器采集 ──┐
              ├─ /sfu-ws ─ 屏幕 SFU ─ 网页观看端
Windows 采集 ─┘                    └─ 原生观看端

原生客户端 ───── /voice-ws ─ 房间语音 SFU
```

组件职责：

- 控制服务负责身份、房间、成员、共享租约、媒体阶段和兼容版本。
- 屏幕 SFU 只负责 WebRTC 信令和屏幕媒体转发，不作为成员列表事实来源。
- 网页适配层负责浏览器采集、SFU host/viewer 生命周期、统一成员展示和旧媒体抑制。
- 原生客户端负责 Windows 采集、原生编码、SFU host/viewer 生命周期和统一成员展示。
- Screego `/stream` 在迁移后仍可维持网页房间页面外壳，但不再传送屏幕 RTP。
- 房间语音保持独立服务、独立信令和独立音频设备生命周期。

### 4.1 实施边界与源文件合同

- `server/register.py` 与 `server/screego/deploy/register.py` 必须保持字节一致，并在每次提交和部署前校验 SHA-256。
- 生产使用的 `sfu-client.js` 当前不在本地仓库中。实施前必须从广州节点的维护副本取得、校验生产摘要，并纳入 `server/screego/deploy/` 管理；不得直接修改无法复现的服务器孤本。
- Screego 上游版本继续由现有锁定文件和补丁流程管理。成员挂载锚点必须作为可重复应用、可测试和可回滚的补丁提交。
- 网页脚本、Screego 补丁、控制服务和客户端变更分别提交，便于逐层验证和回滚。
- 屏幕 SFU 继续使用现有 host/viewer 协议。若灰度测试证明现有服务不能满足统一 H.264/Opus 合同，应停止实施并单独设计 SFU 协议升级，不在本任务中临时改写生产协议。
- 所有服务器改动先在仓库形成可审计产物，再上传临时路径、校验并原子替换。

## 5. 控制面模型

### 5.1 房间状态

`RoomState` 增加并稳定以下字段：

```json
{
  "room": "room-id",
  "active": true,
  "origin": "web",
  "mediaMode": "sfu",
  "mediaProtocolVersion": 1,
  "sharing": true,
  "sharePhase": "live",
  "shareOwnerParticipantId": "participant-id",
  "shareOwnerName": "display-name",
  "shareOrigin": "web",
  "sfu": true,
  "audioMode": "system",
  "participantCount": 2,
  "ttl": 15
}
```

规则：

- `origin` 只表示房间首次创建来源，不决定加入界面或媒体路径。
- `mediaMode` 允许 `sfu` 或迁移期的 `legacy-p2p`。
- `mediaProtocolVersion=1` 表示当前 GameCast SFU host/viewer 信令合同。
- 新版网页端和客户端创建的房间默认 `mediaMode=sfu`。
- 同一房间在一次有效共享期间不得更改 `mediaMode`。
- `sharing=true` 表示存在有效共享租约，包括准备和停止阶段。
- `sfu=true` 仅在 `sharePhase=live` 且 SFU 媒体已经就绪时返回。
- 旧字段继续返回，直到旧网页脚本和旧客户端退出兼容周期。

### 5.2 Presence

每个客户端进程和网页标签页拥有独立且稳定的会话级 `participantId`：

```json
{
  "participantId": "participant-id",
  "room": "room-id",
  "name": "display-name",
  "clientType": "client",
  "role": "member",
  "active": true,
  "mediaProtocolVersion": 1,
  "capabilities": {
    "sfuViewer": true,
    "sfuHost": true,
    "h264": true,
    "opus": true
  },
  "sharing": false,
  "ttl": 15
}
```

规则：

- Presence 加入后立即读取一次成员列表，每 3 秒刷新一次。
- Presence 每 5 秒续约，15 秒未续约即失效。
- 成员按 `participantId` 去重，不按用户名去重。
- 同一账号同时加入网页端和客户端时显示两条成员记录，并显示来源标签。
- 共享状态由共享租约派生，成员不能自行声明为共享者。
- 协议能力用于迁移期拒绝半兼容媒体，不用于按观看端选择不同媒体路径。

### 5.3 共享租约和阶段

共享状态机为：

```text
idle -> starting -> live -> stopping -> idle
```

租约至少包含：

```json
{
  "room": "room-id",
  "leaseId": "lease-id",
  "participantId": "participant-id",
  "mediaMode": "sfu",
  "phase": "starting",
  "audioMode": "off",
  "ttl": 15
}
```

规则：

- `claim` 原子地从 `idle` 进入 `starting`，并立即锁定其他共享入口。
- 共享端只有在捕获、编码器、ICE 和媒体轨就绪后才能更新为 `live`。
- 观看端只在房间为 `sharing=true`、`sharePhase=live`、`sfu=true` 时连接 SFU。
- 正常停止先进入 `stopping`，关闭媒体轨和 PeerConnection 后再释放租约。
- 捕获取消、编码失败、SFU 超时或进程异常退出最终都释放或过期租约。
- 非租约所有者不能更新阶段、续约或释放租约。

## 6. 房间创建与加入

### 6.1 网页端

1. 网页端完成 Screego 房间握手。
2. 以 `clientType=web` 注册 Presence；首次创建时携带 `origin=web`。
3. 使用统一 Presence 渲染完整成员列表。
4. 房间空闲时不建立屏幕 PeerConnection。
5. 房间共享进入 `live` 后，以 viewer 身份连接 `/sfu-ws`。

### 6.2 原生客户端

1. 客户端点击任意房间后直接注册 Presence。
2. `origin=web`、`origin=client` 或兼容期缺失来源均进入原生房间界面。
3. 删除基于房间来源返回 `open-browser` 的正常加入决策。
4. 房间空闲时保持 Presence 和房间状态轮询。
5. 房间共享进入 `live` 后，以 viewer 身份连接 `/sfu-ws`。

### 6.3 离开

两端按以下顺序离开：

1. 若持有共享租约，则停止并释放共享。
2. 关闭屏幕 SFU 连接。
3. 停止房间状态与质量上报。
4. 注销 Presence。
5. 页面或进程异常关闭时由 15 秒 TTL 收尾。

## 7. 网页成员列表

网页端不再克隆 `.MuiListItem-root`，也不再根据名称扫描 Screego 文本。

实施时在 Screego 成员区域增加一个稳定的 PartyLAN 挂载锚点。该改动通过现有 Screego 上游补丁机制完成，只增加容器和必要的生命周期钩子，不改变登录、房间、主题或基础布局。注入脚本完全拥有该锚点内的内容，并按 `participantId` 渲染：

- 成员名称。
- 网页端或客户端来源。
- 房主或成员角色。
- 当前共享者状态。
- 当前成员标识。

迁移期可保留 Screego 原成员数据用于对照，但 PartyLAN 统一成员区域是跨端成员事实展示。全量验收后移除旧 DOM 克隆逻辑。

## 8. 共享媒体流程

### 8.1 网页端共享

1. 检查浏览器 H.264 和 Opus 能力。
2. 领取共享租约并进入 `starting`。
3. 调用 `getDisplayMedia` 获取用户选择的窗口或屏幕。
4. 根据选择来源应用网页共享音频隔离策略。
5. 显式优先 H.264，并以 host 身份连接 `/sfu-ws`。
6. ICE 和媒体发送就绪后把租约更新为 `live`。
7. Screego P2P PeerConnection 不添加屏幕视频或共享音频轨。

浏览器不支持兼容编码、用户取消授权或 SFU 启动失败时，释放租约并显示本地化错误。不得静默发布原生客户端无法解码的 VP8 或 VP9。

### 8.2 原生客户端共享

1. 领取共享租约并进入 `starting`。
2. 根据选择启动窗口或全屏 Windows 原生采集。
3. 默认以原生分辨率和 60 FPS 启动 H.264 编码。
4. 根据音频模式生成独立 Opus 共享音轨。
5. 以 host 身份连接 `/sfu-ws`。
6. ICE、编码器和媒体发送就绪后把租约更新为 `live`。
7. 根据统一质量报告动态降低或恢复分辨率、帧率和码率。

### 8.3 观看

- 网页端与客户端使用相同的房间、角色和协议版本接入 `/sfu-ws`。
- 网页端由 `GC_SFU` 管理浏览器 PeerConnection。
- 客户端由 Go/Pion 管理 PeerConnection 和原生 H.264 解码。
- 观看端可以在共享开始前进入房间，但只在 `live` 后建立屏幕媒体连接。
- 观看端重连必须保持当前 `participantId` 和连接 generation，旧连接的迟到事件不能覆盖新连接。

## 9. 编解码与画质

统一媒体合同：

- 视频：H.264。
- 共享音频：Opus，48 kHz，双声道。
- 房间语音：独立 Opus 轨，仅通过 `/voice-ws`。

网页端在创建发送 transceiver 后显式设置 H.264 codec preference。客户端继续生成 H.264 静态轨。自动测试必须解析双方 SDP，真实验收必须确认最终 selected codec，而不是仅检查能力列表。

网页端和客户端观看端继续上报丢包、往返延迟、解码帧率、卡顿和接收码率。共享端使用统一质量输入：

- 原生共享默认原生分辨率和 60 FPS。
- 弱网时按现有自适应控制器降级。
- 指标恢复并满足稳定窗口后逐级恢复。
- 服务器总出口预算继续限制多观众场景的安全码率。
- 单个观看端不得通过切换到 P2P 获得不同媒体会话。

## 10. 音频隔离

### 10.1 原生窗口共享

- 只采集目标窗口所属进程树音频。
- 不回退到系统混音。
- PartyLAN、自身 WebView、未知来源和不支持的进程只发布视频。

### 10.2 原生全屏共享

- 采集系统播放音频。
- 排除 PartyLAN 进程树和房间语音播放路径。
- 不把 `/voice-ws` 收到的语音重新送入共享音轨。

### 10.3 网页共享

- 窗口共享只请求浏览器提供的窗口音频。
- 全屏共享请求系统音频。
- 浏览器未提供所请求音轨时保持视频共享，并明确显示音频不可用。
- 不接受来源类型与请求模式不匹配的意外音轨。

Windows 真实设备上的语音与共享音频隔离是完成门禁，自动或合成音频测试不能替代。

## 11. 故障处理

- SFU 不可用：显示明确错误，执行有限重试，不自动切换 P2P。
- `starting` 超时：停止捕获并释放租约。
- Presence 过期：停止对应质量上报；共享者 Presence 失效时租约随之失效。
- viewer 断开：在同一 generation 内有限重连；成功连接后使旧回调失效。
- 协议版本不兼容：保持成员可见，阻止不兼容媒体连接并提示更新。
- 编解码不兼容：共享前失败，不进入只有声音或只有画面的状态。
- 成员不可见：分别记录 Presence 请求、返回成员数、渲染成员数和挂载状态。
- 未知错误：显示稳定本地化通用提示，并在日志保留结构化错误码和阶段。

新增或复用的错误码包括：

- `media_protocol_unsupported`
- `codec_unavailable`
- `sfu_unavailable`
- `share_start_timeout`
- `share_locked`
- `share_lease_invalid`
- `share_lease_expired`
- `participant_not_found`

日志不得记录密码、会话令牌、Authorization、SDP、ICE candidate 或媒体内容。

## 12. 渐进式迁移

迁移顺序：

1. 记录服务、镜像、运行依赖、证书、账号文件、配置和前端脚本摘要。
2. 创建可恢复的时间戳备份，不删除旧镜像或持久数据。
3. 先部署向后兼容的控制面字段和状态机。
4. 部署网页统一 SFU 代码，但默认保持关闭。
5. 构建取消浏览器跳转的候选客户端，但不向普通用户发布。
6. 仅对测试房间启用 `mediaMode=sfu`，用候选客户端完成四种共享与观看组合。
7. 更新网页静态资源版本，使新打开或刷新的页面加载统一 SFU 脚本；已进行中的 P2P 共享保持原链路直到结束。
8. 停止向缺少 `mediaProtocolVersion=1` 能力的旧网页标签页发放新的 P2P 共享租约，返回 `media_protocol_unsupported` 并要求刷新页面。
9. 将所有新共享默认切换到 SFU，并确认有效旧 P2P 共享连续至少 30 秒为零。
10. 发布取消浏览器跳转的客户端，并验证客户端加入网页来源房间。
11. 完成全量成员、音频、弱网和网页回归验收。
12. 从正常流程移除 P2P，保留一个发布周期的房间级回滚开关和旧镜像。

迁移期间同一个有效共享会话只能有一个 `mediaMode`。不得在共享中途改变，也不得让不同观看端选择不同模式。

## 13. 测试设计

### 13.1 控制服务

- 房间来源不再影响媒体模式或加入决策。
- 新房间默认 SFU，旧房间可保持迁移期 P2P。
- 共享阶段只允许合法状态转换。
- 并发 claim 只有一个成功。
- `starting`、`live` 和 `stopping` 均锁定第二个共享者。
- 非租约所有者不能更新阶段或释放租约。
- Presence 和租约 TTL 正确清理。
- 协议版本与能力字段正确返回。
- 兼容窗口内旧网页参与者可以完成既有 P2P 共享，但切换门禁启用后不能领取新的 P2P 租约。
- 旧字段和旧接口在兼容周期内保持有效。

### 13.2 网页端

- 网页加入房间后注册并续约 Presence。
- 独立成员挂载点按 `participantId` 渲染网页端和客户端成员。
- Screego React 重绘不会删除 PartyLAN 成员列表。
- 网页共享只向 SFU PeerConnection 添加屏幕媒体轨。
- Screego P2P PeerConnection 不发送屏幕 RTP。
- H.264 codec preference 和 Opus 音频协商正确。
- 捕获取消、SFU 失败和页面离开均释放租约。
- 网页首页、登录、建房、加入和原有主题不回归。

### 13.3 原生客户端

- `origin=web`、`origin=client` 和缺失来源均选择原生 viewer。
- 房间加入不调用 `BrowserOpenURL`。
- 两端 Presence 成员正确合并并显示来源。
- 网页共享能够由原生 H.264 viewer 解码并播放 Opus 共享音频。
- 原生共享能够被网页和客户端同时观看。
- 默认原生分辨率、60 FPS 和动态画质策略保持有效。
- 窗口和全屏共享音频隔离保持有效。
- viewer 重连不被旧 generation 回调破坏。

### 13.4 端到端矩阵

必须完成：

1. 网页共享到网页观看。
2. 网页共享到客户端观看。
3. 客户端共享到网页观看。
4. 客户端共享到客户端观看。
5. 网页和客户端同时在房间时，双方成员在 3 秒内互相可见。
6. 同账号双端显示两条带来源标签的成员记录。
7. 两端同时点击共享时只有一个取得租约。
8. 共享开始、停止、再次开始和异常退出后无残留共享者。
9. 共享中途加入的观看端能够收到音画。
10. 多观众加入和退出不会中断其他观看端。
11. 弱网下降级并在网络恢复后逐级恢复画质。
12. Windows 真实设备验证窗口音频、系统音频和房间语音完全隔离。
13. 网络统计确认正常 SFU 房间没有通过 Screego P2P 发送屏幕 RTP。

## 14. 部署与回滚

部署前必须：

- 记录生产文件 SHA-256、服务状态、容器镜像 ID 和端口监听。
- 备份 `/root/screego` 运行文件、`/var/www/screego` 静态文件、Nginx 配置、systemd 单元、运行环境文件和账号文件。
- 保留现有证书、用户数据、历史记录、运行依赖和容器镜像。
- 在临时服务或测试房间完成兼容验证。

部署后必须：

- 验证 `partylanapp.com` 首页、登录、注册、建房和加入。
- 验证控制面、屏幕 SFU、语音 SFU 和 Nginx 健康状态。
- 核对公开静态文件与维护副本摘要一致。
- 完成桌面和移动视口的网页视觉回归检查。
- 完成真实网页端与客户端跨端验收。

回滚时：

- 先关闭新房间的 SFU 默认开关。
- 恢复同一备份批次的网页脚本、控制服务和配置。
- 恢复旧不可变镜像，不覆盖或删除新旧账号和证书。
- 不回滚仍然有效的用户数据。
- 再次验证网页访问、旧 P2P 房间和服务状态。

生产部署、服务重启和全量切换需要独立确认，不由设计文档提交自动授权。

## 15. 完成标准

同时满足以下条件才算实现完成：

- 客户端加入网页来源房间不再打开浏览器。
- 所有新版网页端和客户端屏幕媒体均通过 `/sfu-ws`。
- 四种跨端共享与观看组合全部通过。
- 两端成员列表均来自统一 Presence，客户端成员在网页端稳定可见。
- 同一房间不存在两个有效共享者或两个媒体模式。
- 最终 SDP 与统计证明使用 H.264 和 Opus。
- 默认原生分辨率、60 FPS 和动态画质没有回退。
- Windows 真实设备证明共享音频不包含房间语音。
- 广州节点网页访问、登录、建房和加入没有回归。
- 自动测试、构建、真实设备和生产验收结果分别记录，不互相替代。

## 16. 非目标

- 不支持同一房间多路同时共享。
- 不增加服务器转码或新的视频编码格式。
- 不把房间语音迁移到屏幕 SFU。
- 不重写 Screego 登录和完整房间页面。
- 不让单个观看端自行回退到 P2P。
- 不在本设计中删除旧镜像、账号、证书、历史或持久数据。
