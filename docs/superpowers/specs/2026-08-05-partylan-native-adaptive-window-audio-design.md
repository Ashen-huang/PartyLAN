# PartyLAN 原生动态画质与窗口音频修复设计

## 1. 背景与结论

PartyLAN 原生 GameCast 主播链路已经具备单轨动态画质控制：客户端结合本机采集、编码
指标和观看端上报，在同一 H.264 轨道上降档并在条件恢复后升档。当前体验仍有两项
缺口：共享弹窗默认选择 `1280 x 720 / 30 FPS`，且“Original”没有中文化；窗口音频
直接绑定窗口所属 PID，对 Chromium、Electron 等多进程应用可能无法覆盖实际持有音频
会话的兄弟进程，因此视频正常但共享音轨没有目标声音。

本设计采用已确认的方案 A：只增强 Windows 客户端，保留现有单轨全局动态画质模型，
将默认设置改为“原始画质 + 60 FPS”，并新增安全的窗口到应用进程树音频解析。整屏
共享继续捕获排除 PartyLAN 进程树后的系统音频。广州节点网页端、共享 SFU、Nginx、
接口路径和服务端数据结构均不修改。

客户端与网页端在本设计中对齐的是“画质能够根据实时条件自动下降并恢复”的能力，
不是复制网页端逐观看者独立调整的实现。原生客户端仍只发布一条视频轨道，因此任一
确认弱网的观看者会触发该共享的全局降档。

## 2. 范围

### 2.1 目标

- 共享弹窗将“Original”中文化为“原始画质”。
- 客户端首次打开共享弹窗时默认选择“原始画质”和 `60 FPS`。
- 原始画质使用所选屏幕或窗口的实际像素尺寸，不放大、不裁切。
- 原生共享根据本机媒体状态和观看端反馈自动降档，并在稳定后逐级恢复。
- 窗口共享自动捕获所选窗口或其安全应用进程树的音频。
- 无法区分同一应用的多个窗口时，允许捕获该应用的全部音频。
- 全屏共享捕获系统输出音频，同时排除 PartyLAN 及其子进程产生的声音。
- 麦克风和 PartyLAN 房间语音在软件媒体图中均不能进入共享音轨。
- 音频失败只关闭共享音频，不中断视频共享或房间语音。
- 生成独立的 `v0.5.6` Windows 客户端包并保留 `v0.5.5` 回滚包。

### 2.2 非目标

- 不为原生客户端增加多层同时编码、Simulcast 或逐观看者独立画质选择。
- 不修改共享 SFU 的单轨发布模型或信令协议。
- 不修改 `/api/quality` 的路径、请求字段、响应结构或服务端策略。
- 不修改广州节点网页资源、Nginx、容器、systemd 服务或部署配置。
- 不让网页端加入 PartyLAN 原生房间语音频道。
- 不增加共享音频手动选择器、音量混音器、录音或转写功能。
- 不承诺 Windows 能区分同一应用进程树中的不同窗口或浏览器标签页。
- 本设计和后续客户端交付不包含广州节点服务重启或重新部署。

## 3. 不可破坏的约束

1. `VoiceSession` 独占麦克风、房间语音 Opus 编解码和语音 RTP 轨。
2. 共享音频解析器只能返回来源策略生成的 Windows 进程回环目标，不能接收语音轨、
   麦克风设备或任意外部音频源。
3. 窗口共享只能使用 `CaptureIncludeProcessTree`；不得回退到系统混音。
4. 全屏共享只能使用 `CaptureExcludeProcessTree(partylanPID)`；排除能力不可用时只发布
   视频，不得回退到 `CaptureSystemMix`。
5. PartyLAN、WebView2、自身进程树、系统进程、目标未知或目标已退出时不得发布该目标
   的共享音频。
6. 候选窗口应用树和 PartyLAN 进程树必须双向无重叠：候选不能属于 PartyLAN 树，
   PartyLAN 也不能属于候选树。
7. 动态画质不得超过用户选择的分辨率和帧率上限，也不得放大低分辨率来源。
8. 视频档位切换、音频重绑定和语音重连必须具有独立生命周期，任何一方失败不得重置
   另外两方。
9. 客户端改动不得要求广州节点新增路由、字段、端口或服务版本。

这些约束由类型边界、策略单元测试、Windows 原生测试和实机数字音频标记共同保证，
不能只依赖 UI 隐藏选项或日志观察。

## 4. 总体架构

```text
RoomToolsDialog
  source + resolution ceiling + FPS ceiling
                    |
                    v
StartNativeGameCastSharing
  resolve actual source bounds
       |                         |
       v                         v
Native video pipeline       ShareAudioResolver
  capture -> NVENC          display -> exclude PartyLAN tree
  Adaptive Controller       window  -> include safe app tree
       |                         |
       v                         v
single H.264 track          independent Opus share track
       |                         |
       +-----------+-------------+
                   v
             existing GameCast SFU

VoiceSession
  microphone <-> dedicated voice PeerConnection
  no reference from or to ShareAudioResolver
```

### 4.1 组件边界

- `frontend/src/components/RoomToolsDialog.tsx` 只负责中文标签、默认值和用户选择的上限。
- `internal/gamecast/adaptive` 继续负责画质阶梯、观察窗口、冷却、恢复、回滚和冻结。
- 新的客户端侧共享音频解析组件负责进程快照、活动音频会话关联和安全目标选择。解析逻辑
  应与 `app.go` 的生命周期编排分离，并允许注入进程与音频会话快照以便单元测试。
- `internal/native/windowsaudio` 继续只负责 Windows 进程回环能力、活动音频会话枚举和
  PCM 帧输出，不接触房间语音对象。
- `app.go` 只负责把已验证的音频目标交给 `ProcessCapturer`，以及在失败时保持视频和
  语音继续运行。

## 5. 视频画质设计

### 5.1 默认值和上限语义

共享弹窗的初始分辨率键为 `original`，初始帧率为 `60`。用户仍可选择固定分辨率或
更低帧率；该选择是本次共享的最大允许档位，而不是关闭动态调整。

“原始画质”解析为所选来源的实际边界，宽高只为编码要求取偶数，不进行放大或裁切。
固定分辨率继续保持长宽比并限制在来源边界内。`normalizeShareFPS` 继续把最大值限制为
`60 FPS`。

### 5.2 动态档位

动态控制器以实际请求档位作为第 0 级，并按不超过该请求的原则加入以下标准档位：

```text
requested
  -> 1920x1080@60
  -> 1920x1080@45
  -> 1920x1080@30
  -> 1280x720@30
  -> 1280x720@24
  -> 960x540@24
  -> 640x360@24
  -> 640x360@18
```

高于 1080p 的原始来源可以从原始 `60 FPS` 降到 `1080p60`；低于某一标准档位的来源
跳过该档位，避免反向放大。码率随档位降低，并受现有安全出口预算约束。

### 5.3 触发和恢复

降档继续综合以下信号：

- 本机新鲜采集帧率、编码帧率和编码时间预算；
- 编码或写入失败；
- 观看端确认的丢包、抖动、接收码率、解码帧率和丢帧；
- 广州节点现有 `/api/quality` 快照中的有效观看者样本和出口预算。

观察窗口确认弱网或本机负载后每次只下降一级。条件稳定并持续满足恢复窗口后每次只
恢复一级。由于原生发布为单轨，任一有效观看者确认弱网即可触发全局降档；无效、过期、
换代或样本不足的数据不得触发切换。

### 5.4 无缝切换和失败处理

新档位编码器在后台准备，并先产生 IDR 关键帧；IDR 成功写入同一轨道后才替换旧编码
器，观看端不重新入房。准备或写入失败时回滚原档位。连续切换失败后进入临时冻结，
避免分辨率反复跳变或黑屏；冻结结束后重新观察，不跳过安全检查。

## 6. 窗口音频目标解析

### 6.1 输入和输出

解析器输入包括所选 `HWND`、窗口 PID、PartyLAN 根 PID、当前 Windows 用户会话内的
进程快照和活动音频会话。进程快照至少包含 PID、父 PID、可执行文件身份和 Windows
会话身份。输出是唯一的安全目标：

```text
TargetProcessID + CaptureIncludeProcessTree + application identity + resolution reason
```

解析器不返回多目标混音列表，也不返回 `CaptureSystemMix`。

### 6.2 确定性选择顺序

1. 重新验证窗口仍然有效、PID 非零且进程存在。
2. 拒绝 PartyLAN、WebView2、系统阻止列表或与 PartyLAN 树双向重叠的窗口进程。
3. 如果窗口进程树已经包含匹配的活动音频会话，直接选择窗口 PID。
4. 否则从窗口 PID 向父级查找最近的安全应用祖先。查找只能停留在同一 Windows 用户
   会话和可证明的应用边界内，不得跨越 Explorer、服务宿主、系统壳层或其他阻止进程。
5. 若某个安全祖先同时包含窗口分支和匹配的活动音频会话分支，选择最近的该祖先。
6. 若应用当前没有活动音频会话，选择最高的安全同应用祖先，以便后续启动的音频子
   进程自动进入捕获；无法证明同应用祖先时保留安全的窗口 PID。
7. 最终候选再次执行进程存活、应用身份和 PartyLAN 双向无重叠检查，任一检查失败则
   返回仅视频策略。

“同应用”通过进程关系、Windows 会话和规范化可执行文件完整路径共同证明：相同完整
路径属于同一应用；不同文件只有在具有直接祖先关系、位于同一安装目录且均不是通用
启动器或系统壳层时，才允许归为同一应用族。完整路径无法读取、安装目录不同或关系
不明确时不得向父级提升。该规则允许 Chrome、Edge、Electron 等应用提升到安全的
浏览器或应用根进程，但不允许按显示名称、窗口标题模糊匹配，也不允许提升到 Explorer
等公共祖先。

### 6.3 同应用多窗口

Windows 进程回环不能可靠区分共享同一进程树的多个窗口或标签页。用户已接受在无法
唯一映射时捕获该应用的全部音频。此降级只扩大到已证明的同一应用树，不能扩大到其他
应用或系统混音。

### 6.4 重试与重绑定

音频捕获首次启动失败时，刷新窗口、进程和活动会话快照并重新解析一次。只有重新解析
结果仍属于同一安全应用时才允许第二次启动。

运行中发生致命捕获错误时，每次共享最多执行一次同应用重绑定。重绑定必须重新验证原
`HWND` 和应用身份，不能根据相似进程名绑定其他程序。重绑定失败后发布
`audio-disabled` 运行时事件并继续无音频视频共享，不进行无限重试。

静音内容和暂时没有播放声音不是错误。系统无法可靠区分“合法静音”和“错误目标”，
因此不能仅凭 PCM 全零自动切换到更大的进程树。

## 7. 全屏音频和语音隔离

全屏共享固定生成以下目标：

```text
TargetProcessID = current PartyLAN PID
Mode = CaptureExcludeProcessTree
```

该模式捕获系统输出中的其他应用声音，同时排除 PartyLAN 根进程及 WebView2 等子进程
产生的房间语音播放。麦克风属于独立输入设备，且从未传入共享音频链路。

若 Windows 不支持进程树排除、PartyLAN PID 不可验证、Opus 不可用或捕获启动失败，
共享只发布视频。全屏和窗口路径都不得调用 `CaptureSystemMix` 作为回退。

分享 PartyLAN 自身窗口时只发布视频。语音的启动、停止、静音、续签和重连不得触发
共享音频重建；共享音频的启动、失败和重绑定也不得触发 `VoiceSession` 重建。

## 8. 错误处理与可观测性

- 视频启动失败仍按现有主流程返回错误并停止本次共享。
- 音频目标不安全、能力不可用或重试失败时，共享以 `audioMode=off` 继续。
- 音频失败通过现有 GameCast 共享运行时事件显示明确的无音频提示，不弹出阻断对话框。
- 运行时日志记录来源类型、候选 PID、选择原因、拒绝原因、捕获模式和重试次数。
- 日志不得记录 PCM、Opus 负载、语音内容、令牌、SDP 或 ICE 地址。
- 画质日志继续记录请求档位、当前档位、切换原因、回滚和冻结，不记录用户内容。
- 音频失败不得停止视频编码器、共享租约、Presence 或 `VoiceSession`。

## 9. 广州节点网页端保护

本方案不修改以下内容：

- `server/` 和 `server/screego/deploy/` 下的网页与控制服务文件；
- Nginx 配置、Docker Compose、systemd 单元和远端运行目录；
- 屏幕 SFU、语音 SFU、注册控制服务及其端口；
- `/api/quality`、`/sfu-ws`、`/voice-ws` 或其他现有路由；
- 网页端共享、观看、音频捕获和逐观看者自适应代码。

客户端仍只使用现有 `/api/quality` 合同。实现验收必须证明上述路径无源码差异，不对
广州节点执行部署或重启。客户端包生成前后分别对 `https://partylanapp.com` 执行访问、
入房、网页共享和网页观看冒烟验证；该验证只使用现有公开功能，不修改服务器状态配置。

## 10. 验证设计

### 10.1 自动化测试

前端测试至少覆盖：

- “原始画质”中文标签；
- 初始分辨率键为 `original`；
- 初始帧率为 `60`；
- 原始画质请求发送 `width=0`、`height=0`、`fps=60`；
- 用户手动选择较低上限后请求保持该选择。

Go 和原生媒体测试至少覆盖：

- 原始、固定和低分辨率来源的尺寸解析，不放大且保持长宽比；
- 请求档位、完整动态阶梯、降档、恢复、过期样本、失败回滚和冻结；
- 窗口 PID 直接命中音频会话；
- 多进程窗口通过最近安全共同应用祖先命中兄弟音频进程；
- 无活动会话时选择安全应用根并允许后续子进程音频；
- 同应用多窗口允许应用级捕获；
- Explorer、系统进程、PartyLAN 双向树重叠、PID 失效和应用身份不明时拒绝；
- 初始刷新重试和运行中最多一次同应用重绑定；
- 窗口路径永不返回系统混音；
- 全屏路径固定排除 PartyLAN 进程树；
- 音频失败不停止视频、共享租约或房间语音。

验证顺序固定为先运行前端测试和生产构建，再运行普通 Go 测试、原生媒体标签 Go 测试
及客户端构建，避免 Vite 替换嵌入式哈希资源时与 Go 测试竞争。

### 10.2 Windows 实机数字标记

至少使用三个隔离的 PartyLAN 客户端或等效的独立 Windows 音频环境，在接收端分别
记录共享 PeerConnection 音轨和语音 PeerConnection 音轨。为以下来源注入可区分的
数字音频标记：目标窗口、同应用其他窗口、其他应用、PartyLAN 远端语音和麦克风。

窗口共享必须满足：

- 共享音轨包含目标窗口标记；
- 多进程解析后仍能在实际发声音频进程中检测到目标标记；
- 不包含其他应用、PartyLAN 远端语音或麦克风标记；
- 无法区分同应用窗口时允许包含同应用其他窗口标记；
- 共享开始、停止和一次安全重绑定均不打断房间语音。

全屏共享必须满足：

- 共享音轨包含目标应用和其他系统应用标记；
- 不包含 PartyLAN 远端语音或麦克风标记；
- 语音重连、静音和恢复不改变共享音轨来源。

### 10.3 弱网和动态画质实测

在支持原始 `60 FPS` 的来源和硬件上记录初始实际发送尺寸、帧率和码率。施加可重复的
带宽、丢包和抖动限制，证明画质至少下降一级；解除限制并保持稳定，证明画质至少恢复
一级。整个过程必须保持同一观看会话，且窗口音频、全屏音频和房间语音均不因视频档位
切换而重建或中断。

### 10.4 网页端无回归

- 客户端实现差异中 `server/`、网页部署资产、Nginx 和 SFU 文件必须为空。
- 客户端交付前后，广州节点均能通过 HTTPS 打开网页并加载静态资源。
- 网页用户能够入房、开始网页共享、停止共享并观看另一发布者。
- 原生客户端共享和动态画质轮询期间，网页端访问与观看仍正常。
- 不通过服务重启或部署来取得验证结果。

自动化测试不能替代 Windows 实机数字标记、弱网恢复和广州节点网页端冒烟证据。

## 11. 交付与回滚

实现通过全部要求后将版本提升为 `v0.5.6`，生成新的
`release/PartyLAN-v0.5.6-win64.zip`，并报告文件大小与 SHA256。现有
`release/PartyLAN-v0.5.5-win64.zip` 及其哈希不得覆盖或删除。

交付审计必须确认生产包不含个人规划文档、测试文件、临时日志、调试数据库或构建缓存。
若原始 `60 FPS`、动态恢复、窗口目标音频、语音隔离或网页端无回归任一项未取得所需
证据，必须明确标为未完成，不能仅凭编译或自动化测试宣称发布完成。

## 12. 验收标准

满足以下全部条件才可结束实现：

1. 共享弹窗默认显示“原始画质”和 `60 FPS`，手动上限仍有效。
2. 原生视频在同一轨道上能够自动降档并恢复，且不超过用户上限。
3. 普通单进程和已覆盖的多进程窗口都能捕获目标应用声音。
4. 同应用多窗口只按已接受的应用级边界降级，不泄漏其他应用声音。
5. 全屏共享包含系统应用声音并排除 PartyLAN 房间语音。
6. 窗口和全屏共享音轨均不包含 PartyLAN 语音或麦克风。
7. 音频失败只使共享转为视频，不影响视频、Presence 或语音频道。
8. 广州节点网页端文件和服务配置无修改，网页访问、入房、共享和观看冒烟通过。
9. 新 `v0.5.6` 包通过生产内容审计并提供大小和 SHA256，`v0.5.5` 回滚包保持原样。
