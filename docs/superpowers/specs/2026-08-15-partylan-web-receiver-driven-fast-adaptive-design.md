# PartyLAN 网页端接收反馈驱动的快速自适应设计

**日期：** 2026-08-15
**状态：** 设计已确认，等待文档复核

## 背景与问题

广州节点实测确认当前 `adaptive-per-peer-v4` 已经按发送 `RTCPeerConnection` 维护状态，但仍未把观看端质量报告精确绑定到对应发送连接。自适应样本中的 `receiverImpaired` 被固定为 `false`，共享端实际只能依据自身发送统计和浏览器带宽估算作出决策。

这造成两类直接故障：严重限速时，浏览器带宽估算随已降低的发送码率收缩，现有“相对上次降档还需再下降约 25%”的条件会阻止继续降档，使画面停在 `540p21`、实际只有 `1-3 FPS`；解除限速后，发送端缺少对应观看者的恢复证据，probe 可以在没有改善观看效果时错误提交，也可能长期没有条件启动。刷新网页能够恢复只说明连接和估算器被重置，并不是有效的自动恢复。

服务器、TURN 和 Screego 在相关测试期间没有重启或媒体错误，问题边界位于网页端自适应策略与接收反馈绑定，不以更换传输链路解决。

## 范围

本轮只修改生产 Screego 浏览器 P2P/TURN 链路中的逐观看者自适应：

- 每个观看者的接收报告精确作用于其对应的发送 `RTCPeerConnection`；
- 严重受损时快速下降到可持续档位；
- 解除限速后由真实接收改善验证逐级恢复；
- 保持已确认的网页质量阶梯和手动质量上限语义；
- 增加足以复现实测决策的内部诊断数据。

屏幕 SFU、语音 SFU、客户端原生媒体算法、SDP、ICE、媒体轨道和 Screego 信令协议不在本轮范围内。现有客户端与网页端的房间和媒体兼容性必须保持不变。

## 质量阶梯

继续使用当前已部署的质量层，不重新定义分辨率或码率上限：

| 源条件 | 自适应顺序 |
| --- | --- |
| 720p 或更低源 | 源分辨率 60/45/30/21 FPS -> 540p21 -> 360p18，且不得放大源 |
| 高于 720p 的源 | 原生 60/45/30 FPS -> 720p30/21 -> 540p21 -> 360p18 |

手动选择的分辨率和帧率是本次共享的质量上限，而不是固定输出层。以 `720p60` 为例，自适应可以下降到 `720p45/30/21` 及更低层；链路恢复后也必须能够逐级返回 `720p60`，不能固定停留在 `720p30`。

## 精确会话绑定

### Screego 前端钩子

PartyLAN 的 Screego 源码补丁在 `hostSession` 和 `clientSession` 创建 peer session 后调用一个可选的 PartyLAN 全局钩子，传入：

- `RTCPeerConnection` 实例；
- Screego 分配的 `sid`；
- 对端 `peerId`；
- 当前连接角色 `host` 或 `viewer`。

`sid` 已同时出现在同一媒体会话的 host/client session 事件中，可作为两端一致的连接键。钩子只是把 Screego 已知的本地运行时元数据交给注入脚本，不增加或更改任何 WebSocket 消息、SDP 属性、ICE 候选或媒体编码格式。PartyLAN 注入脚本尚未加载或钩子执行失败时，Screego 必须继续按原行为建立连接。

### 质量报告与快照

观看端每个自适应采样周期提交现有接收统计，并增加经过长度和格式约束的 `screegoSessionId`。控制面按以下复合键保存最新样本：

`roomId + viewerParticipantId + screegoSessionId`

质量样本保持短期内存数据，不持久化 SDP、ICE、令牌、媒体内容或账号凭据。超过有效期的样本从快照排除并清理。

共享端每个采样周期只拉取一次当前房间快照，再按 `screegoSessionId` 映射到各自的发送连接。禁止把房间最差观看者、无法识别的 participant 或不匹配的 session 样本应用到其他连接。

质量快照授权扩展到当前网页共享者。服务端必须同时验证调用者属于目标房间、是当前共享者/房主、participant 身份与 Presence 一致。现有原生客户端授权路径保持兼容。

### 缺失与过期处理

接收报告缺失、超过三个采样周期未更新、会话不匹配或授权失败时，该连接标记为 `receiver-unavailable`，只使用连接自身的发送统计作保守判断。缺失反馈不得被解释为接收质量良好，也不得触发跨连接降档。

## 快速降档

自适应保持约两秒一个采样周期。接收侧严重受损需要连续两个有效样本确认，以过滤页面切换、统计刚启动和单次网络尖峰。

严重受损由同一会话的发送与接收统计共同判定，包括：

- 共享端仍持续编码和发送，但观看端解码帧率低于对应发送帧率的一半或低于 `8 FPS`；
- 共享端持续发送，但观看端连续基本没有新解码帧；
- 观看端实际接收码率显著低于该连接的发送码率，并伴随持续丢包、抖动恶化或解码帧率下降；
- 有效可用带宽已经低于当前质量层的最低承载门槛，且接收质量同步恶化。

判定时以同周期发送帧率作为参照。源窗口静止、最小化或采集端本身没有产生足够新帧时，单独的低解码帧率不能被判为网络拥塞。

首次确认严重受损时立即下降一层。应用新层并经过一个采样周期后，如果同一观看者仍严重受损，则根据有效带宽、实际接收吞吐和层最低承载门槛，直接选择能够稳定承载的最高较低层，不再逐层等待常规冷却。约 `1 Mbps` 且实际只有 `1-3 FPS` 的连接应在约 `6-10 秒`内从高层到达 `360p18`，不能停在 `540p21`。

当前“相对上次降档还需继续恶化约 25%”只保留为发送端估算器单独下降时的级联保护。出现精确绑定的接收受损，或有效容量已低于当前层门槛时，允许继续降档。轻微拥塞、短暂抖动和只有 `qualityLimitationReason=bandwidth` 的样本仍按逐层策略处理。

达到 `360p18` 后保持最低层，不重复执行无意义的降档调用；但继续记录接收损伤，以便链路恢复后进入升档判定。

## 接收验证的恢复

同一连接连续约六秒满足以下条件后，可以启动一次单档 probe：

- 接收报告持续有效且与 session 精确匹配；
- 观看端解码帧率相对发送帧率健康，没有连续无帧；
- 丢包和抖动的平滑趋势稳定或改善；
- 没有新的严重受损样本；
- 可用带宽达到下一层参考需求，或当前层持续健康且浏览器估算因发送上限而没有自然回升。

probe 只提升一层，并记录提升前的发送码率、接收码率、发送/解码帧率、丢包和抖动作为基线。观察窗口内，只有对应观看者的解码帧率、实际接收吞吐或呈现连续性达到预期改善，且没有新增损伤，才提交新层。

以下任一情况立即回退：连续两个坏样本、接收报告过期、解码帧率明显下降、连续无帧、丢包显著恶化，或应用参数失败。probe 没有产生可观测改善时也不得作为成功提交。

失败后使用短冷却并按连续失败次数增加等待，避免同一临界带宽反复振荡；成功后重新累计稳定时间，继续逐级恢复。一次抖动尖峰只影响平滑趋势，不清空全部稳定进度；持续异常才阻止升档。

## 状态与诊断

每个发送连接独立维护：

- `screegoSessionId` 和对端标识；
- 最近的有效接收样本及更新时间；
- 发送与接收帧率、码率、丢包、抖动的平滑值；
- 接收损伤连续次数和具体原因；
- 当前层、最近降档层与容量基线；
- 稳定累计时间；
- probe 层、基线、截止时间、结果和冷却；
- 参数应用失败及回退状态。

质量诊断样本增加但不限于以下字段：策略版本、session 是否绑定、发送与接收 participant、当前/目标层、有效容量、发送/接收码率、发送/解码帧率、损伤原因、稳定时长、probe 门禁与结果、换档原因。字段只用于内部质量接口和日志，不向成员列表或普通房间 UI 暴露。

页面离房、共享停止、peer connection 关闭或 Screego session 被替换时，必须清除对应绑定、自适应定时器、probe 和过期质量样本，防止旧观看者数据污染新连接。

## 错误处理与兼容性

- Screego 元数据钩子不存在时，连接按现有媒体流程正常建立，自适应退回发送统计模式。
- 控制面质量接口失败时不得停止共享、关闭媒体轨道或重建 peer connection。
- `RTCRtpSender.setParameters` 失败时保留原层并记录错误，probe 视为失败。
- 不识别新增质量字段的旧控制面或旧网页继续忽略字段；新控制面对缺少 session 的旧网页继续接受基础质量样本，但不将其用于精确接收决策。
- 原生客户端、屏幕 SFU 和语音 SFU 不消费新增网页 session 字段，行为保持不变。

## 测试与验收

自动测试必须覆盖：

- Screego host/client session 使用相同 `sid` 绑定到各自 peer connection；
- 多观看者环境下，弱网报告只改变对应发送连接；
- 无 session、错误 session 和过期报告不污染其他连接；
- 严重受损连续确认后先降一层，持续受损时跳到可持续层；
- 约 `1 Mbps` 下 `540p21` 可以继续下降到 `360p18`；
- 短暂异常、静止源和单独 bandwidth 标记不会误触发快速降档；
- 解除限速后无需刷新即可从 `360p/540p/720p` 逐级恢复；
- probe 必须由对应观看者的接收改善确认，失败或报告过期会回退；
- `720p60/45/30/21` 手动上限能够降档并恢复到原选择；
- 页面离房、停止共享和连接替换会清理状态；
- 策略源、部署副本、缓存版本、Python/Node/Go 回归和前端生产构建通过。

线上灰度在 `test` 房间验证 P2P、TURN、单观看者、多观看者和限速恢复。验收以观看端实际解码帧率、收到的分辨率/码率和连续画面为准，不能只以共享端调用 `setParameters` 成功或 probe 状态提交为准。

## 部署与回滚

部署前分别备份生产静态目录、维护副本、Screego 源码补丁/镜像信息、控制面文件和 Nginx 中将要修改的精确版本字符串。不得用本地维护 Nginx 配置覆盖生产完整配置。

精确 session 钩子需要重建并短暂重启 Screego，在线 Screego 房间会断开并需要重新加入。质量快照授权和存储变更需要短暂重启控制面。屏幕 SFU、语音 SFU和无关服务不重启。

发布顺序为兼容的控制面、Screego/静态资源、缓存版本和灰度验证。每步执行语法、摘要、进程、容器和 HTTP 资源检查。若出现房间无法建立、session 无法匹配、多观看者互相影响、快速换档振荡、解除限速仍不能恢复、服务异常或新增协议兼容问题，则停止灰度并按本次独立备份恢复。
