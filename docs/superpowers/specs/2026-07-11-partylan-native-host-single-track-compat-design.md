# PartyLAN 原生 Host 单路视频兼容设计

## 1. 背景与结论

客户端自建房间后，网页端观看原生客户端共享时只有声音、视频黑屏。窗口共享已稳定复现；整屏共享与窗口共享复用同一条原生视频发送链路，因此按相同缺陷处理。

本轮日志已经排除网页播放器挂载、客户端捕获和 H.264 编码停滞：

- 客户端持续产生并写入三层 H.264 样本；
- Opus 音频轨正常进入 SFU 并转发给网页端；
- SFU 没有触发任何视频 `OnTrack`；
- SFU 对三个视频 SSRC 均报告 `incoming SSRC failed Simulcast probing`。

根因是原生客户端使用 Pion WebRTC v4 发送带 RID 的三层 simulcast，而当前 SFU 使用 Pion WebRTC v3。双方虽然能完成 SDP 协商，但 SFU 无法从实际入站 RTP 中完成 RID 探测，因而在视频轨建立前丢弃三个 SSRC。

## 2. 目标

1. 恢复客户端自建房间的原生视频共享，使网页端能够观看。
2. 同时覆盖窗口共享与整屏共享。
3. 保留现有 H.264 编码、分辨率、帧率、码率控制和关键帧请求能力。
4. 保持共享音频实现不变。
5. 不修改网页端主题、布局、全屏交互和音频来源隔离行为。

## 3. 非目标

- 本轮不升级 SFU 的 Pion 主版本。
- 本轮不恢复原生 Host 的多层 simulcast。
- 本轮不重构窗口或整屏捕获实现。
- 本轮不调整网页 Host 的共享链路。
- 本轮不重新设计多观众带宽分配策略。

## 4. 方案选择

### 4.1 采用方案：单路标准 H.264 轨道

原生 Host 只创建一条不带 RID 的 `TrackLocalStaticSample` 视频轨道，并通过一次 `AddTrack` 发布。不再为视频调用 `WithRTPStreamID` 和 `RTPSender.AddEncoding`，SDP 中不再声明 `rid` 与 `simulcast`。

窗口共享和整屏共享继续使用各自现有捕获器，但统一把编码结果写入这条标准视频轨道。发送分辨率、帧率和目标码率仍取当前共享配置；关键帧生成与服务器 PLI 请求处理保持不变。

当前 SFU 已实现无 RID 视频回退：当房间只有一条普通视频轨道时，无论网页 viewer 请求 `q`、`h` 或 `f`，`TrackSnapshot` 都会返回该唯一视频轨道。因此服务器和网页 viewer 不需要为本次兼容修复改代码。

### 4.2 暂不采用：协商失败后自动重连

先尝试 simulcast，等待服务器回报视频轨状态，失败后再重建 PeerConnection 为单路模式。该方案需要新增服务端信令、超时和重连状态，会延长首帧时间并引入更多会话竞态，不适合作为紧急修复。

### 4.3 暂不采用：统一升级到 Pion v4

升级 SFU 并修复完整 simulcast 互通可以保留分层转发，但会同时影响 Host、viewer、ICE、RTP 转发和部署回滚面。它应作为后续独立项目，在跨版本端到端测试完善后实施。

## 5. 数据流

修复后的原生视频链路：

`窗口/整屏捕获 -> 单路 H.264 编码 -> 无 RID 视频轨 -> SFU OnTrack -> 唯一视频轨回退 -> 网页 video`

音频链路保持：

`系统/进程音频捕获 -> Opus 音频轨 -> SFU OnTrack -> 网页 audio/video`

## 6. 行为与兼容性

- 单观众：使用共享配置对应的单路画质，不再被错误地限制到 `q` 层。
- 多观众：所有观众接收同一上行视频层，服务器仍分别转发；暂时没有按观众选择不同分辨率的能力。
- 原生 viewer：继续接收标准视频轨，不要求理解 RID。
- 网页 viewer：现有请求层参数保留，SFU 自动回退到唯一视频轨。
- 音频：窗口进程音频、整屏系统音频及手动关闭行为均不变。

## 7. 失败处理与可观测性

- 视频轨创建或加入 PeerConnection 失败时，沿用现有会话启动失败路径并返回明确错误。
- 保留视频发送样本数、码率和会话数日志。
- 新增或调整启动日志，明确记录 `single-track` 发送模式，便于和旧 simulcast 日志区分。
- 不通过静默切回旧媒体路径掩盖错误。

## 8. 测试策略

先建立失败测试，再修改实现：

1. SDP/PeerConnection 测试确认原生 Host 只声明一条 H.264 视频轨。
2. 确认 SDP 不包含 `a=rid` 和 `a=simulcast`。
3. RTP 接收测试确认对端能够触发视频 `OnTrack` 并读到 H.264 RTP，而不只验证 SDP 字符串。
4. 回归音频轨、关键帧请求、窗口共享和整屏共享共用的发送生命周期。
5. 运行 `go test ./internal/gamecast/...` 及受影响的应用层测试。
6. 构建客户端后，在客户端自建房间中分别验证：
   - 窗口共享，网页端有画面和声音；
   - 整屏共享，网页端有画面和声音；
   - 停止后重新共享；
   - 网页 viewer 在 `q` 请求下仍能收到唯一视频轨。

## 9. 发布与回滚

本轮预计只需要发布 Windows 客户端，不重启 SFU、不替换网页资源。发布前保留现有客户端构建产物；若出现回归，可回退到上一客户端版本。

恢复 simulcast 必须作为后续变更进行，并以 Pion v4 Host 到实际 SFU 的 RTP 级互通测试作为启用条件，不能只依赖 SDP 中存在 RID 声明。
