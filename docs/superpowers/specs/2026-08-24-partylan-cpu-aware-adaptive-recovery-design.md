# PartyLAN CPU 感知的网页自适应与恢复设计

**日期：** 2026-08-24
**状态：** 设计已确认，等待书面复核
**范围：** Screego 原生 P2P/TURN 网页共享链路

## 背景

`xiusxiu` 房间实测中，三条长连接均使用 TURN/UDP，接收侧绝大多数样本丢包接近零、RTT 和发送队列延迟稳定，且没有服务端码率保护上限。然而发送端长期报告 `qualityLimitationReason=cpu`。当前自适应策略把“采集帧率正常但编码/发送帧率下降”合并进接收端 `receiver-low-fps`，继而按网络异常快速跨级降档。结果是健康观看者可从高画质迅速跌至 `540p` 或 `360p`，并因恢复探测要求接收 FPS 或码率提升至少 15%，长期无法升回。

页面进入后台后，接收反馈会变稀疏或过期，现有探测又把反馈缺失算作失败。诊断界面同时使用用户配置的 `50Mbps` 原始目标估算 TURN 负载，持续显示并不存在的服务器带宽超限。以上三类问题相互叠加，使实际故障看起来像网络或服务端限速。

## 目标与非目标

### 目标

- 将发送端 CPU 压力与接收端网络异常拆成独立信号，避免 CPU 崩帧触发网络快速降档。
- CPU 受限时优先保留分辨率，按既有画质阶梯逐级降低帧率。
- 严重且有新鲜接收证据的网络异常可以快速降档，但单次最多跨两级。
- 恢复探测适用于静态屏幕内容，不再依赖 FPS 或实时码率必须提高固定百分比。
- 页面隐藏或接收反馈过期时冻结策略；恢复新鲜反馈后继续判断。
- 服务器容量提示以当前档位和实际流量为依据，不再使用原始配置目标制造假警报。

### 非目标

- 不修改 Screego 信令、SDP、TURN 服务、媒体协议或房间 Presence 协议。
- 不增加全局共享者 CPU 协调器；每个观看者继续维护独立 PeerConnection 和自适应状态。
- 不改变已确认的画质阶梯、手动分辨率/FPS 上限或用户选择。
- 不改变客户端原生采集与编码策略；本次只修复网页共享策略。
- 不把自适应媒体切回 SFU。

## 方案选择

采用在现有每观看者自适应策略内增加 CPU/网络分类的方案。它保留当前 P2P/TURN 架构和独立观看者画质，仅修正错误信号和状态机。

未采用以下方案：

- 完全交给 Chromium：改动最少，但无法保证既定画质阶梯、恢复节奏和诊断可见性。
- 增加共享者级全局 CPU 协调器：可统一多个编码器的 CPU 预算，但需要跨 PeerConnection 聚合与同步，风险和验证范围明显更大。本轮稳定后可依据实测决定是否另行设计。

## 设计

### 1. 信号分类

策略为每个有效样本计算互斥的主要压力类型。沿用当前阈值：活跃帧率为 `8 FPS`，明显退化比例为 `0.5`，健康比例为 `0.75`，接收健康要求丢包低于 `3%` 且平滑抖动不高于 `100ms`。

- `cpu`：浏览器报告 `qualityLimitationReason=cpu`，且接收帧率达到实际发送帧率的 `0.75`；或采集达到 `8 FPS`，但编码/发送帧率低于 `max(8, 采集帧率 × 0.5)`，同时接收帧率达到实际发送帧率的 `0.75`。
- `network`：实际发送达到 `8 FPS`，但接收低于 `8 FPS` 或低于实际发送帧率的 `0.5`；或吞吐缺口与超过 `5%` 的丢包/超过 `100ms` 的抖动共同出现。
- `healthy`：接收帧率与实际发送帧率匹配，丢包和抖动处于健康范围，且没有 CPU 压力。
- `unavailable`：页面隐藏、样本无效、接收反馈未绑定或反馈已过期。

“采集 60 FPS、编码/发送 3 FPS、接收 3 FPS”属于 `cpu`，不得再标记为 `receiver-low-fps`。“发送 60 FPS、接收 3 FPS”才属于接收端解码或网络异常。

现有 `qualityLimitationReason=bandwidth` 仍只是辅助信息，不能在缺少吞吐、丢包或接收退化证据时独立触发降档。

### 2. CPU 降档

CPU 路径只允许普通 `downshift-cpu` 决策，禁止调用网络快速跨级逻辑：

1. 连续两个有效 CPU 样本确认压力后降一级。
2. 每次降档后遵守现有降档冷却窗口，再重新累计 CPU 样本。
3. 既有阶梯天然先降低同分辨率帧率，例如 `1080p60 → 1080p45 → 1080p30`、`720p60 → 720p45 → 720p30 → 720p21`。
4. 只有冷却后 CPU 压力仍连续存在，才允许跨入下一个较低分辨率档位。
5. CPU 样本不得设置 `lastDownshiftReceiverDriven`，也不得成为后续网络快速降档的起点。

这样可以快速缓解单个编码器负载，同时避免一次 CPU 波动直接牺牲分辨率。

### 3. 网络降档

普通网络异常沿用连续样本确认和逐级降档。第一次确认后，如果后续新鲜接收反馈仍显示严重异常，可按可持续带宽计算目标档位，但单次最多跨两级。例如 `L1` 最多跳到 `L3`，不能直接跳到 `L6`。

快速降档必须同时满足：

- 当前压力类型为 `network`；
- 接收报告已绑定、未过期且报告 ID 为新；
- 上一次降档也是接收端网络证据驱动；
- 已经过快速降档等待窗口；
- 目标档位低于当前档位且不超过两级跨度。

持续 `1Mbps` 等严重限速仍会通过多次短间隔判断到达低档，但不会因单个噪声样本直接触底。

### 4. 恢复探测

所有恢复均保持一次升一级。探测不再要求接收 FPS 或实时码率比探测前提高 15%，因为静态画面不会稳定满足该条件。

网络降档后的探测提交条件为：

- 至少两个新鲜、有效的接收报告；
- 报告均未被分类为 `network`；
- 丢包、抖动和发送/接收帧率比例保持健康；
- 探测窗口内没有两个明确异常样本。

CPU 降档后的探测还要求浏览器不再报告 CPU 限制，且编码/发送帧率不再明显落后于活跃采集帧率。对于静止画面或采集本身不活跃的情况，不以绝对 FPS 作为失败条件。

探测只有连续两个明确的同类压力样本才回滚。回滚后保留现有递增冷却，避免快速反复升降。

### 5. 后台和反馈缺失

样本为 `page-hidden`、无效，或原本依赖的接收报告过期时：

- 不追加坏样本；
- 不触发普通或快速降档；
- 不提交或回滚恢复探测；
- 保留当前档位和探测状态。

重新取得至少两个新鲜有效样本后，状态机才继续作出决定。探测的墙钟截止时间可以已经过去，但样本不足时必须继续等待，不能仅因超时回滚。

### 6. 服务器负载诊断

诊断中的单流估算值改为：

`max(当前自适应档位 maxBitrate, 当前实测上行, 当前实测下行)`。

它不再包含用户最初配置但已被档位约束的 `computeTargetBitrate()`。SFU/TURN 建议容量和估算负载继续基于该单流值计算，保持保守的档位上限，同时消除固定 `50Mbps` 导致的假超载。

此数据只用于显示和日志，不参与实际自适应决策或编码上限。

### 7. 状态与诊断兼容性

- 策略版本从 `adaptive-per-peer-v5` 升级为 `adaptive-per-peer-v6`，用于区分新旧实测数据。
- 保留现有档位编号和 profile 字段，控制面 JSON 结构保持向后兼容。
- 决策类型增加 CPU 可辨识标记，网络快速降档仍保留独立类型，便于线上按原因统计。
- Nginx 中策略资源从 `webrtc-adaptive.js?v=7` 升为 `v=8`，注入脚本从 `inject.js?v=6.27` 升为 `v=6.28`，确保浏览器不会继续加载旧实现。
- `test?adaptive=baseline` 继续保留浏览器基线对照；其他使用自定义策略的房间加载新版本。

## 错误处理

- `getStats()` 失败或样本计数器重置：本轮样本记为 unavailable，不改变档位。
- 接收质量上报重复：只更新显示，不重复计入确认或探测样本。
- 接收报告过期：冻结依赖接收反馈的策略，不猜测网络异常。
- CPU 与网络证据同时出现：若接收帧率能跟随已降低的发送帧率，则分类为 CPU；若发送保持活跃而接收独立退化，则分类为网络。

## 测试与验收

先新增会在旧实现上失败的单元和集成测试，再修改实现。

自动测试至少覆盖：

- 采集 60、发送 3、接收 3 且 CPU 受限时，只产生逐级 CPU 降档，不产生接收异常或快速触底；
- CPU 持续时按同分辨率 FPS 档逐级下降，跨分辨率前必须经过新的确认窗口；
- 发送 60、接收 3 且网络证据充分时仍能快速降档，但一次最多跨两级；
- 健康复杂画面和单独 `bandwidth` 标记不会误降档；
- 恢复探测在接收 FPS/码率没有提升 15% 时，只要连续新鲜反馈健康仍可提交；
- 探测期间页面隐藏、报告过期或重复报告不会回滚；恢复两个新鲜样本后继续提交或按真实异常回滚；
- CPU 恢复探测在 CPU 限制持续时回滚，CPU 压力解除后可逐级恢复；
- 诊断负载使用当前档位上限，不使用原始 `50Mbps` 目标；
- 源策略与部署策略字节一致，静态资源版本同步升级；
- 现有 720p、1080p、1440p、4K 画质阶梯和服务器预算测试保持通过。

本地验收运行全部 Node、Python 和相关构建检查。代码完成后不直接改变线上服务；线上部署和 `test` 灰度需另行确认。

## 线上灰度建议

部署前备份 `webrtc-adaptive.js`、`inject.js` 和 Nginx 配置。先在 `test` 房间执行以下组合：

- 单观看者和三观看者，观察 CPU 受限时只逐级降 FPS；
- 分别限制为 `1Mbps`、`5Mbps` 后解除，确认可到达低档并逐级恢复；
- 静态桌面和复杂运动画面，确认恢复不依赖固定码率增幅；
- 共享端和观看端分别切后台再恢复，确认档位冻结且不锁死；
- 观看者退出再加入，确认每条连接状态独立。

若出现网络严重拥塞无法及时降档、CPU 路径跨级触底、恢复再次锁死、后台缺反馈仍改变档位，或网页兼容性异常，恢复本次独立备份。
