# PartyLAN 原生共享启动稳定性设计

## 1. 背景

2026-07-13 的原生客户端复测暴露出两个启动阶段问题：

1. 观众刚开始观看共享时，画面会在“流畅几秒”和“停住几秒”之间反复，随后才稳定。
2. 窗口或全屏共享开始时如果没有正在播放的音频，之后再开始播放，观众仍听不到声音。

本设计只处理客户端原生 Host 共享链路。网页端采集、页面样式、房间来源协议和带宽自适应不在本轮范围内。

## 2. 证据与根因

### 2.1 视频采集阻塞了 RTP 发送节奏

`runGameCastVideoLoop` 当前在同一 goroutine 中依次执行等待帧位、捕获、编码和 `WriteSample`。窗口捕获最多阻塞 250 ms，全屏 DXGI 捕获也可能短暂无帧。捕获超时后循环直接跳过本次发送，但下一次 H.264 样本仍使用固定的 `1 / FPS` 时长。

复测日志显示启动阶段每 2 秒编码帧数从 39、26、23、28 逐步恢复到约 50；全屏路径还出现连续的 `frame temporarily unavailable`。因此真实墙钟时间和 RTP 媒体时间在启动阶段失配，浏览器 jitter buffer 会表现为交替流畅和停帧。采集稳定后，该现象自然消失。

### 2.2 启动关键帧请求放大了抖动

一次原生 Host 建连会依次触发连接成功、SFU track-start、viewer-answer 和 viewer-connected 等关键帧请求。日志中约 3 秒内出现了四次 NVENC 强制 IDR。每个 IDR 都会携带 SPS/PPS 并产生大包突发，在视频发送节奏尚未稳定时进一步增加解码和缓冲压力。

### 2.3 无声启动时 SFU 没有及时发现音频轨

原生音频采集把 `timeout` 和 `buffer empty` 当作可重试状态，因此采集线程本身不会因为无声退出。但是在没有 PCM 数据时，当前实现不会发送任何 Opus RTP。

SFU 的 Host `OnTrack` 只有收到首个 RTP 包后才发现轨道。观众建连时，SFU 最多等待约 1 秒收集 Host 轨道；如果这段时间只有视频 RTP，观众 PeerConnection 将只协商视频轨。之后音频开始播放时，即使 Host 开始发送 Opus，SFU 也不会为已经连接的观众动态增加音轨。

这解释了窗口和全屏共享都会出现“无声启动后永远没有声音”。

### 2.4 窗口音频还存在同名进程 PID 误选

窗口源目录已经包含由窗口句柄解析出的 `ProcessID`，但前端启动原生共享时只传递进程名。无活动音频会话时，后端退回进程列表，并从多个同名进程中选择一个 PID。Edge、Chrome 等应用有多个同名 renderer/utility 进程，选中的 PID 可能不是共享窗口所属进程，也不包含之后真正播放音频的同级进程。

## 3. 目标

- 原生窗口和全屏共享启动后，视频 RTP 按配置 FPS 保持稳定时间轴。
- 短暂捕获无帧时不让发送循环停顿；已有画面时重复最近一帧。
- 启动阶段重复 PLI 不造成连续 IDR 突发，同时不影响连接后的正常丢包恢复。
- 开始共享时没有声音，也要立即建立音频 RTP 轨；之后播放音频无需重启共享或重新协商。
- 窗口共享优先捕获所选窗口对应的准确进程树。

## 4. 非目标

- 不通过增加固定播放延迟掩盖问题。
- 不在本轮修改 SFU 的带宽分配、码率自适应或多层 simulcast。
- 不修改网页端 `getDisplayMedia` 行为。
- 不把音频捕获失败静默降级为无限静音；永久错误仍应上报并关闭音频共享。
- 不恢复全屏 DXGI 长时间完全无帧时的画面内容；本轮只保证取得首帧后的短暂抖动不破坏发送节奏。

## 5. 设计

### 5.1 视频采集与发送解耦

原生视频循环拆为两个职责：

1. 采集 worker 调用现有窗口或全屏 capturer，将最新有效帧写入容量为 1 的 mailbox。新帧覆盖尚未消费的旧帧，避免积压和延迟增长。
2. 发送 loop 使用配置 FPS 的 ticker。每个 tick 读取 mailbox 中的最新帧并保存为 `lastFrame`，随后编码并发送 `lastFrame`。

行为规则：

- 尚未取得首帧时不发送伪造画面。
- 已取得首帧后，暂时没有新帧就重复最近一帧。
- 每个成功发送的 H.264 样本使用 ticker 的固定帧时长，RTP 时间轴与墙钟发送节奏一致。
- mailbox 永远只保留最新帧，不建立播放队列，不额外增加启动延迟。
- 采集返回可重试错误时保留 `lastFrame` 并限频记录日志。
- 采集返回永久错误时沿用现有失败处理并停止共享。
- 取消共享时同时取消采集 worker 和发送 loop；底层捕获停止仍使用现有有界等待，避免 UI 永久卡住。

### 5.2 启动关键帧合并

在原生客户端的关键帧应用层增加时间门控，不修改 SFU 协议：

- 连接后的第一个关键帧请求立即执行。
- 视频循环启动后的前 5 秒内，1.5 秒窗口中的重复请求被合并并标记为已处理。
- 启动窗口结束后，只合并 300 ms 内的重复请求，避免异常 PLI 风暴，同时保留正常丢包恢复能力。
- 被合并的请求记录 debug 日志，但不调用 NVENC `ForceKeyFrame`。

该策略把典型启动阶段的四次 IDR 收敛为最多两次，不依赖推测网络质量，也不会把偶发网络波动判为劣质链路。

### 5.3 从共享开始发送 Opus 静音帧

音频发送 loop 改为由 20 ms ticker 驱动：

- 每个 tick 优先使用捕获队列中的最新 PCM 帧。
- 本 tick 没有 PCM 数据时，编码一个 48 kHz、双声道、20 ms 的全零 PCM 帧。
- 共享开始后 20 ms 左右即可产生首个 Opus RTP，使 SFU 在观众建连前发现音频轨。
- 真实 PCM 到达后自然替代静音，不创建新轨、不重新协商 PeerConnection。
- 捕获的 `timeout` 或 `buffer empty` 继续视为正常无声状态。
- 捕获、Opus 编码或 RTP 写入的永久错误继续触发现有音频失败流程，不用静音掩盖故障。

静音包只用于维持已启用的共享音频轨；用户选择关闭共享音频时不创建音频轨，也不发送静音包。

### 5.4 窗口音频使用准确 PID

原生共享请求增加可选的 `audioProcessId`：

- 共享设置从选中的 `ShareSource.processId` 传递该字段。
- `audioMode=process` 时，后端优先使用非零 `audioProcessId`，并以 `CaptureIncludeProcessTree` 启动 Windows process loopback。
- 未提供 PID 的旧调用继续按进程名解析，保证兼容现有绑定和测试。
- `audioMode=system` 继续使用 PID 0 的系统 loopback。
- PID 已退出或启动失败时沿用现有“音频关闭、视频继续”的运行时提示，不随机切换到另一个同名进程。

## 6. 数据流

视频：

`capturer -> latest-frame mailbox -> FPS ticker -> NVENC -> Pion H264 track -> SFU -> viewer`

音频：

`process/system loopback -> latest PCM or silence -> 20 ms ticker -> Opus -> Pion audio track -> SFU -> viewer`

两条链路都以发送时钟为节奏源。采集端只负责更新最新可用数据，不再决定 RTP 时间轴是否前进。

## 7. 测试策略

### 7.1 视频单元测试

- 脚本化 capturer 依次返回有效帧、多个暂时无帧错误、恢复帧。
- 断言取得首帧后发送次数按 ticker 前进，暂时无帧期间仍重复最近帧。
- 断言 mailbox 不积压旧帧，恢复时发送最新帧。
- 断言永久捕获错误只上报一次并结束循环。
- 断言启动关键帧时间门控会合并重复请求，启动窗口后恢复较短门限。

### 7.2 音频单元测试

- 无 PCM 输入时仍按 20 ms 节奏向 sink 写入 Opus 包。
- 若干静音 tick 后注入真实 PCM，断言 loop 不重启即可继续写包。
- `timeout` 和 `buffer empty` 不关闭音频 loop。
- 永久捕获错误仍触发失败回调。
- 指定 `audioProcessId` 时优先使用该 PID；未指定时保留按名称解析的兼容路径。

### 7.3 回归与构建

- `go test ./...`
- `go test -tags partylan_native_media ./...`
- 前端类型检查与生产构建。
- 使用 `Start-PartyLAN.ps1` 重新构建带原生媒体、原生捕获和原生编码的客户端。

## 8. 实际复测验收

1. 窗口共享在静止画面和动态画面下各启动三次，观众首屏后不再交替停顿。
2. 全屏共享启动三次；取得首帧后短暂 DXGI 无帧不导致 RTP 发送停顿。
3. 窗口共享开始时保持无声，观众连接后再播放音频，5 秒内应听到声音且无需重启共享。
4. 全屏共享勾选系统音频，在无声状态启动；观众连接后再播放音频，5 秒内应听到声音。
5. 关闭共享音频时确认没有音频轨和静音包。
6. 停止窗口和全屏共享均能在有界时间内退出。

## 9. 回滚边界

- 视频调度器、关键帧门控、Opus 静音调度和 `audioProcessId` 传递保持为独立改动，可分别回滚。
- 不修改房间状态、Presence、Share Lease 或网页兼容 Host 协议。
- 若固定节奏视频发送导致异常 GPU 占用，可单独回滚视频 mailbox，音频修复仍可保留。
