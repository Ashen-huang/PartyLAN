# PartyLAN 网页与客户端自适应恢复、触底保护设计

**日期：** 2026-08-10
**状态：** 设计已确认，等待实施计划

## 目标

修复深度实测暴露的三类问题：网页端解除限速后不会自动升档、复杂画面在实际观看流畅时被误降档，以及客户端观看/共享端因带宽估算器跟随发送码率下降而连续降档触底。

本设计只调整质量层策略、恢复状态和客户端层调度，不改变 Screego P2P、TURN、SFU、音频采集或房间协议。网页端和客户端使用相同的质量语义，但保留 JavaScript 与 Go 各自的运行时实现。

## 已确认的质量阶梯

质量层按源分辨率选择：

| 源条件 | 质量阶梯 |
| --- | --- |
| 720p 或更低源 | 保留源分辨率的 60/45/30/21 层 -> 540p21 -> 360p18；源分辨率不足时不得放大 |
| 高于 720p 的源 | 原生60 -> 原生45 -> 原生30 -> 720p30 -> 720p21 -> 540p21 -> 360p18 |

复杂画面编码上限：

| 层 | 上限 |
| --- | ---: |
| 720p60 | 12 Mbps |
| 720p45 | 9 Mbps |
| 720p30 | 6 Mbps |
| 720p21 | 4 Mbps |
| 540p21 | 2.5 Mbps |
| 360p18 | 0.8 Mbps |

高分辨率源的原生层上限为：1080p 60/45/30 使用 16/12/8 Mbps，1440p 使用 24/18/12 Mbps，4K 使用 40/30/20 Mbps。TURN/SFU 仍受广州节点 160 Mbps 安全预算约束，P2P 不分摊该预算。

每层同时定义参考码率和降档门槛。编码上限允许复杂画面短时超过参考值，实际发送超过参考值本身不能触发降档。最低层固定为 360p18 / 800 Kbps。

## 网页端策略

`server/webrtc_adaptive_policy.js` 是唯一策略源，`server/screego/deploy/webrtc-adaptive.js` 必须保持字节一致。`computeEncodingProfile` 输出当前层的编码上限、参考码率和降档门槛；现有观察窗口、逐级变更和路径重置接口保持兼容。

### 降档

- `qualityLimitationReason=bandwidth` 不能单独触发降档。
- 坏样本必须有独立的传输或呈现劣化佐证，例如持续低可用发送带宽并伴随低吞吐、丢包、抖动，或接收质量报告中的帧率/丢帧恶化。
- 降档确认继续使用最近样本窗口和连续坏样本要求。
- 一次降档后记录当时带宽估算；下一次降档还必须证明估算相对上次降档进一步恶化约 25%，或出现新的接收侧劣化，防止估算器跟随发送码率下降造成级联。
- 达到 360p18 后进入 `floor-protected`，重复坏样本只更新诊断状态，不再产生新的降档动作。

### 恢复 probe

- 当前层连续健康 8 秒后最多逐级尝试恢复一层。
- 有效带宽达到下一层参考值 105% 时可启动 probe；即使带宽估算未明显上升，只要丢包、抖动和呈现指标持续健康，也允许启动一次 probe。
- probe 通过 `RTCRtpSender.setParameters` 应用更高层参数，观察 6 秒。
- 两个坏样本或明确带宽限制立即退回原层，并进入恢复冷却；成功则提交新层并清空恢复计时。
- 网页刷新不再是恢复的必要条件。

## 客户端策略

### 逐观看者层

`internal/gamecast/adaptive/per_viewer.go` 继续负责单个观看者的层目标和层池选择：

- 观看者网络反馈只改变该观看者的层，不改变共享端全局编码层。
- 状态增加上次降档估算、probe 状态、probe 截止时间和触底保护标记。
- 带宽估算低于当前层不能单独造成连续降档；二次降档必须满足进一步恶化比例或接收侧丢包、丢帧、解码帧率等独立信号。
- 触底后固定在 360p18，直到稳定 probe 成功。
- probe 逐级切换观看者层；失败立即切回原层，成功后进入升档冷却。

### 共享端本地压力

`internal/gamecast/adaptive/controller.go` 只处理采集、编码和传输写入压力。观看者下行问题仍只进入诊断，不触发共享端全局降档。

`gamecast_p2p_media.go` 和 `gamecast_layer_pool.go` 保留聚合编码负载保护，但最低质量层不可被聚合过载清除。高成本层可以被移除或隔离，低负载持续后按现有机制恢复。

## 诊断与错误处理

网页和客户端的决策原因统一表达为：`viewer-network`、`local-capture`、`encoder-overload`、`transport-write`、`probe`、`probe-rollback`、`floor-protected`。参数应用失败不得关闭共享或媒体轨道；保留原层并在下一采样周期重试。

不新增 SDP、RID、编码器协议或服务端转码。服务端质量报告只用于已经存在的身份和房间隔离链路，不输出账号、令牌、ICE、SDP 或媒体内容。

## 测试验收

网页 Node 测试覆盖：

- 720p60/45/30/21 和高分辨率源阶梯；
- 复杂画面超过参考码率不误降档；
- 单独 bandwidth 标记不降档；
- 解除带宽限制后自动逐级 probe 恢复；
- probe 失败回退和 360p18 触底冻结；
- 源策略与部署副本字节一致。

客户端 Go 测试覆盖：

- 720p 源四个帧率层、低于 720p 源不放大和高分辨率源的顺序；
- 单个观看者隔离、级联降档阻断和触底冻结；
- 稳定 probe 恢复与失败回退；
- 聚合编码过载不移除最低层；
- 普通 Go、`partylan_native_media`、服务器 Node/Python、前端测试和生产构建。

## 部署边界与停止条件

部署只允许原子替换网页策略副本、客户端构建产物和必要的静态资源缓存版本；服务端屏幕/语音容器不重启。部署前备份网页策略、Nginx 配置和客户端产物，发布后先做哈希、语法、服务状态和 `test` 房间灰度验证。

出现以下任一情况停止发布并恢复备份：恢复 probe 造成稳定链路振荡、最低层无法维持连续画面、源/部署策略不一致、客户端编码层协议不兼容、Nginx 或房间 API 回归，或需要改变现有媒体协议才能通过测试。
