# PartyLAN 注册服务 bcrypt 原子写入设计

## 背景

生产注册接口在 2026-07-11 复测中多次返回 HTTP 500。服务日志显示
`No such file or directory: 'htpasswd'`，原因是注册服务依赖主机上的
`htpasswd` 命令，但部署没有声明或安装该依赖。账号文件
`/etc/gamecast-sfu/users.htpasswd` 自 2026-06-04 后没有发生写入。

## 目标

- 移除注册服务对外部 `htpasswd` 命令的依赖。
- 继续使用 Screego 可读取的 htpasswd bcrypt 记录格式。
- 保留当前账号文件中的全部用户和密码哈希，不迁移、不重置密码。
- 保持现有注册 API、校验规则和“注册后手动登录”交互不变。
- 防止同一服务进程内的并发请求重复创建用户名或损坏账号文件。
- 写入失败时保留原文件，并返回稳定且不泄露敏感信息的错误。
- 账号文件更新后无需重启 Screego，新用户下一次登录即可被识别。

## 非目标

- 不增加自动登录、找回密码、修改密码或管理员界面。
- 不改变用户名和密码校验规则。
- 不改变 Screego 登录协议或容器认证配置。
- 不在本次修复中调整 WebRTC 码率、ICE 恢复或影子质量策略。

## 设计

### 账号存储

注册服务直接使用已安装的 Python `bcrypt` 模块生成哈希。新增记录保持
`username:bcrypt_hash` 格式，既有记录按原始文本原样保留。密码和完整哈希
不得写入日志、HTTP 响应或测试输出。

活跃账号文件迁移到专用目录
`/etc/gamecast-sfu/users/users.htpasswd`。Docker 将整个专用目录只读挂载到
`/app/users`，Screego 读取 `/app/users/users.htpasswd`。不能继续单独 bind mount
账号文件，因为宿主机原子替换文件后，容器进程仍可能绑定旧 inode，导致热加载
看不到新内容。专用目录只包含密码哈希文件，不包含 `runtime.env` 或其他密钥。

### 并发与原子性

注册服务使用进程内 `threading.Lock` 串行化“读取、检查、生成哈希、写入”
整个事务。systemd 保证生产环境只运行一个注册服务进程，因此该锁覆盖当前
部署中的并发请求。

锁内重新读取账号文件并检查用户名，消除 `user_exists` 与 `add_user` 分离造成
的竞态。新内容先写入账号文件同目录下的临时文件，刷新并 `fsync`，继承现有
文件权限后使用 `os.replace` 原子替换。替换失败时删除临时文件，原账号文件
保持不变。

### 结果与错误处理

底层创建操作返回明确结果：创建成功、用户名已存在、存储失败。HTTP 层映射为：

- 创建成功：HTTP 200，继续提示用户手动登录。
- 用户名已存在：HTTP 409，保持当前提示。
- bcrypt 或文件写入失败：HTTP 500，返回通用“注册失败”，服务端仅记录异常类型
  和安全描述，不记录用户名之外的凭据数据。

现有的空字段、用户名格式和最短密码校验继续返回 HTTP 400。注册频率限制保持
不变。

### Screego 认证热加载

Screego 当前只在启动时读取账号文件。认证模块需要保存账号文件路径、最后一次
成功加载的文件修改标识和受读写锁保护的账号表。每次校验登录前先执行轻量
`stat`；只有文件大小或纳秒级修改时间发生变化时才重新读取并解析账号文件。

重载成功后一次性替换内存账号表并更新修改标识，因此注册服务完成原子替换后，
新用户的下一次登录即可生效，不需要重启容器，也不会中断现有房间。重载期间的
并发登录由锁保护，不得观察到半份账号表。

如果新文件读取或解析失败，Screego 记录不含账号哈希的错误并继续使用最后一份
成功加载的账号表。这样既有用户仍可登录，失败文件修复后下一次登录会再次尝试
重载。

## 测试

先添加会在当前实现上失败的测试，再修改实现：

1. 在临时账号文件中创建用户，不依赖系统 `htpasswd` 命令。
2. 使用 Python bcrypt 验证新记录能够匹配原密码。
3. 创建新用户后，既有账号行逐字保留。
4. 多线程同时注册同一用户名时，仅一个请求成功，其余返回用户名已存在。
5. 模拟 `os.replace` 失败，确认原账号文件内容不变且临时文件被清理。
6. API 测试覆盖 HTTP 200、409 和存储失败的 500 响应。
7. 确认 `server/register.py` 与部署副本保持一致。
8. Go 认证测试先加载旧账号，再原子替换账号文件，确认无需重启即可验证新账号。
9. Go 认证测试写入损坏文件，确认旧账号继续可用且下一次有效更新能够恢复重载。
10. 并发执行账号校验和文件重载，通过 Go race detector 验证账号表无数据竞争。

## 部署与回滚

部署前复制原路径 `/etc/gamecast-sfu/users.htpasswd` 和当前注册服务脚本到带时间戳
的备份目录。创建只包含账号文件的 `/etc/gamecast-sfu/users/`，将原文件复制到
新路径并核对哈希、记录数和权限。更新 runtime 环境中的宿主机账号文件路径及
目录路径，再使用目录挂载启动新镜像。

Screego 认证热加载作为固定上游补丁构建新镜像，保留当前生产镜像用于回滚。
更新镜像和注册脚本后，在隔离目录执行完整的注册、热加载与登录测试，不向生产
账号文件写入测试用户；随后检查服务日志和既有账号登录。

回滚时恢复 compose、runtime 路径和注册服务脚本并重启服务。原路径账号文件在
迁移期间保留为只读回滚副本。只有在活跃账号文件发生异常时才恢复账号文件备份，
避免覆盖部署后真实用户的合法注册。

## 验收标准

- 服务器未安装 `htpasswd` 时，注册仍能成功。
- 新账号立即可以通过现有 Screego 登录接口登录。
- 已有 15 个账号继续可用，文件中不存在明文密码。
- 并发同名注册不会产生重复记录或破坏账号文件。
- compose 使用专用目录挂载；原子替换后容器能观察到新 inode。
- 损坏的账号文件更新不会清空 Screego 内存中最后一份有效账号表。
- Python 自动测试、Go 认证测试与 race detector、隔离注册登录烟雾测试和线上服务
  健康检查全部通过。
